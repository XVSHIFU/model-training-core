# 0.2 可靠性改进与验证边界

这次优化依据真实安装和失败注入暴露的问题，保持原分类算法、上传特征、阈值和模型格式。参考实践资料中的三条方法：从实际入口验证、让证据对应同一次输入、先定义什么状态算完成。已有指南提供调查方向，本项目的测试和运行记录才是本轮验证证据。

## 问题与处理

| 已复现的问题 | 本轮处理 | 验证方式 |
| --- | --- | --- |
| 安装 wheel 后默认结果写进 Python 环境；源码指纹混入无关依赖 | 工作目录与安装位置分离，只登记本发行包的四个 Python 包 | 独立环境安装真实 wheel，从客户工作目录运行四个 CLI 命令 |
| ID 为 null 或数字时被转换成字符串，错误状态与非有限特征延迟暴露 | 样本公共字段严格校验，文本适配器拒绝无效输入 | 空值、类型、状态、数值边界测试 |
| 解析后文件被修改，报告记录的 hash 指向另一批数据 | 一次读取的字节同时用于解析和 SHA-256，运行配置使用深拷贝 | 在解析期间改写源文件、修改调用者配置，核对实际拟合批次 |
| 缺少内容/模板指纹仍可能声称独立 | 记录每行指纹覆盖，检查训练来源和覆盖完整性 | 缺失指纹、重复内容、旧版 lineage 与无训练集测试 |
| JSON 序列化失败会截断上一份运行状态 | 先完整序列化，再通过同目录临时文件原子发布 | 序列化失败、目标占用、并发创建测试 |
| 中断留下 running 状态；文件存在可能被当作可用制品 | 可处理的中断记录 interrupted；只加载成功训练运行的制品 | 中断注入及 running/failed/interrupted/缺记录拒绝加载 |
| 评测失败后用途记录丢失，并发评测可绕过顺序检查 | 本地跨进程锁串行核验，执行模型前登记用途；失败仍保留记录 | 真实子进程互斥、超时、终止释放、故障后再次申请独立资格 |
| 旧 independent 历史未经结构验证就被跳过 | 先完整验证全部记录，再判断哪些用途影响资格 | 坏 JSON、无效成员和用途不一致测试 |
| 每次工程复验覆盖唯一报告，难以关联测试版本 | 每次保存独立报告，分别记录源码、测试、配置、夹具、依赖锁及验证脚本指纹 | 缺工具、缺 XML、执行失败、输入在验证中改变的测试 |

## 为什么保留失败评测的用途

只在评测成功后登记会漏掉“模型已经运行，指标或报告写入失败”的情况。本版在模型执行前登记，失败记录仍影响后续独立资格。这会保守地占用某些实际上尚未算出结果的数据，但避免通过重跑把已使用的数据变成未使用。重复评测同一冻结模型仍可作为复现检查。

锁只管理同一个本地制品目录。它不会跨不同副本或不同模型汇总用途，也不跟踪人工在框架外查看或选型。参与改进的数据仍须在下一版训练配置中登记为 development。移动产物必须复制整个运行目录与评测历史。

## 安装与工作区

`MODEL_TRAINING_HOME` 非空时指定工作区；否则使用调用时的当前目录。默认预测/评测输出为该工作区的 `runs/`，保护配置为该工作区的 `local/protected.json`。训练配置中显式指定的 `run_root` 仍相对于配置文件，CLI 的 `--run-root` 优先。

源码指纹只包含 `training_core`、`training_backends`、`training_tasks`、`upload_judge`；依赖版本单独记录。添加无关依赖文件不会改变项目源码身份。缺失必要包会报错，不退回扫描整个安装环境。

## 升级兼容性

原 joblib、旧上传公共接口与业务输出保持兼容。新框架制品需要完整的成功训练 `run.json`，仅模型文件或半成品不会被视为可加载的完整制品。旧版 lineage 仍可读取；旧记录若无法证明内容和模板指纹覆盖完整，则不能获独立资格，但可以预测或进行历史回归。

JSON 发布使用同目录临时文件和本地文件系统的原子替换/硬链接，新文件不会覆盖并发创建的目标。当前实测环境为 Windows；未验证网络文件系统、断电耐久性或所有操作系统。强制终止来不及写中断状态时，运行可能保留 running，加载器会拒绝把它当成已完成制品。重跑创建新运行，不是恢复中断训练。

## 怎样复验

```powershell
uv sync --locked --extra dev --python 3.11
uv run --locked python scripts/verify_engineering.py
uv run --locked python scripts/verify_wheel.py
```

第一条验证命令检查当前源码工程，第二条构建并安装真实 wheel，在独立环境运行合成流程。两者都把详细报告写到新的 `runs/`，不自动覆盖文档中的已发布报告。公开汇总经审阅后发布，详细报告可能包含本地路径，应留在本地。

当前发布证据见[工程验收](engineering-verification.json)、[安装验收](wheel-verification.json)和[上传兼容验证](verification.json)。合成流程、安装成功和旧输出一致各自证明不同范围，不能据此声称真实业务泛化能力提高。

本轮为 361 项测试通过、0 失败、3 项跳过；跳过的是 Windows 未允许创建符号链接的路径逃逸测试，这些路径不宣称已验证。真实 wheel 的 13 步全部通过，原模型 3,009 条输出完全一致，登记的 173 个原文件未改变。工程与安装报告使用相同的源码、测试、配置、夹具和依赖锁身份。
